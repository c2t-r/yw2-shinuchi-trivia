# ツチノコパンダの出現条件

## 概要

ツチノコパンダは、専用のすれ違いデータを受け取ると、さすらい荘のVIPルームに出現します。
受信時には出現の抽選を行わず、累計すれ違い回数も条件に含まれません。

セーブデータを新しく作るとき、**約1%**の確率で、専用のすれ違いデータを作成できる状態に
なります。対象のデータですれ違い用データを保存すると、通常のチーム情報と一緒に専用データが
作られます。この抽選結果を使って専用データを作成すると、フラグは解除されます。

専用データは1回送信でき、受信した本体にも次の相手へ送るための専用データが保存されます。
受信者が新規データ作成時の約1%の抽選に当たっている必要はありません。
このため、最初に専用データを作成した人から、受信者を経由して別の人へ広がります。

専用データには255回の転送回数が設定され、受信するたびに1減ります。残り回数が0になった
データをゲームが読み込むと、転送回数を255回に戻した専用データを作り直します。
255回は1つのデータを再生成するまでの回数であり、出現回数の上限ではありません。

## 内部処理

### 受信時の出現条件

受信処理は`code.bin`の`sub_60059C`が担当します。
`0x600658`〜`0x60066C`でメッセージの`user_data`を調べ、値が1なら通常の訪問者処理、
2ならツチノコパンダの処理へ進みます。

| 項目 | 通常のチーム情報 | ツチノコパンダ用 |
| --- | ---: | ---: |
| `user_data` | 1 | 2 |
| 本文の大きさ | 2,136バイト | 4バイト |

ツチノコパンダ用の本文には32ビットのカウンターが入っています。
`0x600694`〜`0x6006B8`で、次の式に従って値を更新します。

```text
カウンター = min(本文の値 + 255 - 受信後のforwardCount, 99999)
```

最初に作成したメッセージの本文は0、転送回数は255です。最初の受信では本体側が転送回数を
254に減らすため、ゲーム側で計算するカウンターは1になります。

`0x6006BC`〜`0x6006D8`は、スロット番号1・2・3を指定して`sub_3DB47C`を呼び、
各セーブ枠のイベント番号15へこの値を書き込みます。
`sub_412B7C`は`0x412BE8`で現在のセーブ枠のイベント番号15を読み、0でなければ値を
取り込んでイベント番号15を0へ戻し、次のフラグを立てます。

| フラグID | 種類 | 設定位置 |
| --- | --- | --- |
| `0x3CDB0D89` | グローバル | `0x412C2C` |
| `0x3D12F75F` | ローカル | `0x412C4C` |
| `0x3EFD209C` | ローカル | `0x412C64` |

VIPルームの設定`data/res/map/t103i69/t103i69_npc_set_0.01b.cfg.bin`にある
`NPC_APPEAR sasurai`の出現条件は、次の1条件です。

```text
グローバルフラグ 0x3CDB0D89 == 1
```

受信時の出現登録にもVIPルームの出現条件式にも、乱数による抽選、専用データを作るための
フラグ、累計すれ違い回数の条件はありません。出現条件式には、ストーリー進行、
通常の訪問者数、戦闘済みフラグも含まれていません。

### 新規データ作成時の約1%の抽選

専用メッセージの生成条件には、グローバルフラグ`0xC27065E9`を使います。
新規データ初期化処理`0x3AF2C0`は、`0x3AF350`で乱数を取り、
`0x3AF354`〜`0x3AF360`で`0.01f`以下かどうかを判定します。
条件を満たすと、`0x3AF378`でこのフラグを立てます。

乱数関数`sub_13E82C`は乱数の下位24ビットを浮動小数点数へ変換し、
`0x13E86C`〜`0x13E870`で正規化して、渡された上限値を掛けます。
この呼び出しの上限値は`1.0f`なので、フラグが立つ確率は約1%になります。

### QRコードによる生成条件の設定

コード本体が`P1ZZZZ`で、認証値が正しいQR1コードを読み取ると、
グローバルフラグ`0xC27065E9`が立ちます。
QRの認証を通った後、`sub_3AF92C`の`0x3AF968`〜`0x3AF994`でこのコードを判定し、
`0x3AFA94`でフラグを設定します。通常のアイテム報酬検索や、読み取り済みコード本体との
照合へ進む前の分岐です。読み取りには、コード本体に対応する認証値も必要です。
認証の計算方法は[QRコードの記事](qr-code.md)に記載しています。

### 送信メッセージの作成

すれ違い用データを保存する`sub_60083C`は、既存の送信箱に未送信の専用メッセージが
ある場合、その本文を引き継ぎます。通常の送信データの作成に成功すると、専用メッセージも
作り直します。

既存の専用メッセージを引き継がず、第2引数が0の場合は、`0x600B80`でフラグ
`0xC27065E9`を読み、`0x600B98`で解除します。通常の送信データの作成に成功し、
このフラグが立っていた場合、`0x600BAC`から専用メッセージ作成処理`0x600DF4`を呼びます。

専用メッセージの作成時には、次の値を設定します。

| 項目 | 値 | 設定位置 |
| --- | ---: | --- |
| `sendCount`：送信可能回数 | 1 | `0x600E80` |
| `forwardCount`：転送残り回数 | 255 | `0x600E84` |
| `batchID`：同時送信する組の番号 | 1 | `0x600E90` |
| `user_data`：メッセージの種類 | 2 | `0x600EA8` |

`sendCount`は、その本体に保存されたメッセージを送れる回数です。
`forwardCount`は、受信者を経由して転送できる残り回数です。

### 本体側の転送処理

受信したメッセージを次の送信用に保存する処理は、本体のすれ違い通信モジュール`CECD`が
担当します。この節のアドレスは`CECD`内のものです。

`sub_1031D0`は、`0x103360`〜`0x103364`で受信したメッセージの`forwardCount`を
1減らします。受信箱へ保存した後、残り回数が0でなければ、`0x1033E4`で同じメッセージを
送信箱にも保存します。受信者のセーブでフラグ`0xC27065E9`を立てる処理は必要ありません。

重複判定は、`0x1032E0`から呼ぶ`sub_1112D0`が、現在の受信箱に同じメッセージIDが
あるかどうかを調べます。ゲーム側の受信処理は、処理を終えた後に`0x600810`で受信箱を
空にします。

### 転送回数が0になった場合の再生成

受信後の`forwardCount`が0になると、`CECD`はそのメッセージを送信箱へ保存しません。
ゲーム側の`sub_60059C`は、`0x6006DC`〜`0x6006F0`で残り回数が0かどうかを調べ、
専用メッセージ作成処理`0x600DF4`を呼びます。

この呼び出しには、フラグ`0xC27065E9`の確認も約1%の抽選もありません。
更新した本文のカウンターを引き継ぎ、`sendCount = 1`・`forwardCount = 255`の
新しいメッセージを作ります。

### すれ違い用データの保存し直し

`sub_60083C`は、既存の送信箱に`user_data = 2`のメッセージがあり、`sendCount`が
0でなければ、`0x600944`〜`0x600984`で本文の値に`255 - forwardCount`を加え、
99,999を上限として引き継ぎます。既存の送信箱を空にして通常のチーム情報を作り直した後、
専用メッセージも`forwardCount = 255`で作り直します。

送信済みで`sendCount`が0になったメッセージは、引き継ぎの対象になりません。
次に専用メッセージを受信すると、本体側の受信処理によって送信箱にも保存されます。
